# 소고기 구이용 MVP 개발 명세서

## 1. MVP 범위

첫 MVP는 소고기 구이용 후보 비교에만 집중한다.

사용자는 마트 또는 정육점에서 소고기 후보 2~5장을 촬영하거나 업로드한다. 앱은 사진 기준으로 가장 맛있을 가능성이 높은 후보를 추천하고, 추천 이유와 주의 신호를 보여준다.

이번 웹 프로토타입은 실제 LLM 연동 전 단계로, 브라우저에서 이미지 색상과 밝기 정보를 간단히 분석해 결과 UI와 사용자 흐름을 검증한다.

## 2. MVP 목표

- 30초 안에 후보 사진을 올리고 결과를 확인할 수 있다.
- 후보별 추천 순위와 이유를 볼 수 있다.
- 담백함, 고소함, 부드러움, 가성비 중 하나의 취향 기준을 적용할 수 있다.
- 결과 문구가 과장되거나 식품 안전을 확정하지 않는다.
- 추후 멀티모달 LLM API로 교체 가능한 분석 인터페이스를 만든다.

## 3. 핵심 사용자 흐름

1. 사용자가 웹앱에 접속한다.
2. 소고기 구이용 모드가 기본 선택되어 있다.
3. 사용자가 취향 기준을 선택한다.
4. 후보 사진 2~5장을 업로드한다.
5. 앱이 사진을 미리보기로 보여준다.
6. 사용자가 "분석하기"를 누른다.
7. 앱이 후보 순위, 추천 이유, 주의 신호를 표시한다.
8. 사용자가 "이 후보로 결정" 또는 "다시 비교"를 선택한다.

## 4. 화면 구성

### 4.1 상단 영역

- 제품명
- 현재 모드: 소고기 구이용
- 짧은 가치 제안

### 4.2 입력 영역

- 취향 선택 세그먼트
  - 균형
  - 담백함
  - 고소함
  - 부드러움
  - 가성비
- 이미지 업로드
- 후보 카드 미리보기
- 분석하기 버튼

### 4.3 결과 영역

- 최종 추천 후보
- 추천 이유 요약
- 분석 신뢰도
- 후보별 순위
- 항목별 평가
  - 색 안정감
  - 지방감
  - 지방 분포 추정
  - 표면/포장 주의 신호
- 주의 문구

## 5. 프로토타입 분석 방식

실제 서비스에서는 멀티모달 LLM이 이미지 특징을 구조화해 반환한다.

웹 프로토타입에서는 브라우저 캔버스로 다음 값을 추정한다.

- 평균 밝기
- 붉은색 계열 비율
- 밝은 흰색 계열 비율
- 과도한 밝은 반사 비율
- 어두운 픽셀 비율
- 색상 대비

이 값으로 다음 점수를 계산한다.

- colorScore: 고기 색 안정감 추정
- fatScore: 지방/마블링으로 보이는 밝은 영역 추정
- balanceScore: 과한 반사와 어두움이 적은지 추정
- confidence: 사진 품질 기반 신뢰도

주의:

이 분석은 실제 품질 판정이 아니라 UX 검증용 임시 로직이다.

## 6. LLM 연동 시 목표 JSON

향후 멀티모달 LLM은 다음 형태로 응답해야 한다.

```json
{
  "recommendedCandidateId": "candidate-2",
  "confidence": "medium",
  "summary": "사진 기준으로는 2번 후보가 구이용으로 가장 균형이 좋아 보입니다.",
  "ranking": [
    {
      "candidateId": "candidate-2",
      "rank": 1,
      "score": 86,
      "pros": ["마블링이 비교적 고르게 보임", "색이 안정적으로 보임"],
      "cons": ["포장 반사가 조금 있음"],
      "reason": "구이용으로 볼 때 지방 분포와 색감의 균형이 가장 좋습니다."
    }
  ],
  "notices": [
    "사진 기준 참고용 분석입니다.",
    "유통기한, 냄새, 포장 팽창 여부는 직접 확인해 주세요."
  ]
}
```

## 7. 금지 표현

결과 화면과 LLM 응답에서는 다음 표현을 사용하지 않는다.

- 무조건 맛있습니다.
- 상하지 않았습니다.
- 신선도가 보장됩니다.
- 안전합니다.
- 공식 등급입니다.

## 8. 권장 표현

- 사진 기준으로는 좋아 보입니다.
- 구이용으로 적합할 가능성이 높습니다.
- 색 판단 신뢰도는 보통입니다.
- 포장 반사 때문에 정확도가 낮을 수 있습니다.
- 구매 전 유통기한과 포장 상태를 확인해 주세요.

## 9. 현재 구현 범위

이번 구현은 다음을 포함한다.

- 정적 웹앱
- 이미지 2~5장 업로드
- 후보 미리보기
- 취향 선택
- 클라이언트 측 이미지 휴리스틱 분석
- 추천 순위 표시
- 후보별 이유 표시
- 구매 결정/다시 비교 UI

이번 구현에서 제외한다.

- 실제 LLM API 연동
- 사용자 로그인
- 구매 기록 저장
- 라벨 OCR
- 가격 비교
- 모바일 카메라 직접 촬영 최적화

## 11. LLM 연동 및 비용 제한

현재 프로토타입은 서버의 `/api/analyze` 엔드포인트를 통해 OpenAI 멀티모달 API를 호출한다.

보안 원칙:

- API key는 브라우저 코드에 넣지 않는다.
- API key는 서버에서만 `openai_api_key.txt` 또는 `OPENAI_API_KEY` 환경변수로 읽는다.
- `/api/status`는 key 값이 아니라 설정 여부만 반환한다.
- `openai_api_key.txt`는 `.gitignore`에 포함한다.
- API 요청/응답 로그에 key 또는 이미지 원본을 기록하지 않는다.

비용 제한:

- 1회 실제 LLM 분석 이미지 수 기본값: 3장
- 1일 실제 LLM 분석 호출 수 기본값: 10회
- 1일 라벨 OCR 호출 수 기본값: 15회
- 이미지 전송 전 브라우저에서 긴 변 768px, JPEG 품질 0.72로 축소
- 서버 요청 본문 크기 기본 제한: 약 4.5MB
- 실패한 OpenAI 호출은 일일 사용량에 더하지 않는다.
- OpenAI 호출 실패 시 기존 로컬 휴리스틱 분석으로 fallback한다.

환경변수로 조정 가능한 값:

```powershell
$env:OPENAI_MODEL="gpt-4.1-mini"
$env:MAX_IMAGES_PER_ANALYSIS="3"
$env:MAX_DAILY_LIVE_CALLS="10"
$env:MAX_DAILY_OCR_CALLS="15"
$env:MAX_ANALYZE_BODY_BYTES="4500000"
```
